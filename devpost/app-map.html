Track My Mailbox · project guide

How this proof of concept works

TMM demonstrates how one test-only recipient can record and see a simulated mail-arrival event. The browser keeps events in memory for the open session.

Boundary: This working demo does not detect physical mail, monitor a mailbox, send real email, or provide production authentication or multi-user security.

One action, one visible result

1. Recipient acts

index.html exposes the test-only identity and Simulate Test Arrival button.

2. Browser records

app.js creates a timestamped test event and asks the in-memory store to accept it.

3. UI confirms

After acceptance, the app shows the labeled arrival and success status; a failed write shows a retryable error.

The store-before-display order means the app does not present a successful arrival before the store accepts it. Refreshing the page starts an empty session.

Reference route through the source

Use these three stops to follow the behavior in the current working tree; this route is a reference and is not a claim that it was toured.

Entry point — index.html

Find data-simulate, data-arrivals, and data-status. These anchors connect the button, list, and accessible status region to JavaScript.

Workflow — app.js, mount and recordArrival

mount wires the button to the flow. recordArrival sets the duplicate guard and progress state, waits for the two-frame rendering opportunity, calls the store, then handles acceptance or failure. Successful results also respect the 400 ms minimum busy duration.

Storage and result — app.js, createInMemoryStore and renderArrivals

The store keeps events in a session-local array. After acceptance, renderArrivals displays the timestamp and TEST · SIMULATED label; the status region confirms success.

To change this, start here

  • Purpose, identity, empty state, or action wording: index.html.
  • Recording, progress, failure, retry, or success ordering: app.js → recordArrival.
  • Arrival row contents and labels: app.js → renderArrivals.
  • Button spinner, status colors, or layout: styles.css → .primary-action:disabled and .status[data-state].
  • Behavior evidence: tests/test.html and tests/test.js.

A practice to reuse

Turn “show success after recording” into an observable ordering rule: keep the result hidden while a controlled store write is pending, then check that the event and success appear only after acceptance. TMM’s approved store-before-display criterion, recordArrival, and pending-write test show how one test can verify that boundary in another project too.

Run it locally

From the project root on macOS, open Terminal and run open index.html. To open the browser test harness, run open tests/test.html. The pages use local files without a server or network connection.
